# Vigil 开发与测试工程规范

> 日常小团队流程以 `simple-delivery.md` 为准；本文仅作为需要更大测试矩阵时的参考。

版本：v1.0（初始基线）  
适用范围：`vigil-private` 主线、`vigil-oss` 公开子集、六个单端平台构建及后续新增平台。  
约束：本规范定义流程与验收目标，不表示当前骨架已经实现或达到这些指标。

---

## 1. 可借鉴设计及其落地原则

| 来源 | 可借鉴设计 | Vigil 的采用方式 | 明确不照搬的部分 |
|---|---|---|---|
| CatAntiCheat | 每个校验环节独立任务、deadline、完成标记和超时原因 | 统一 `TaskTracker`，会话、截图、扫描共用一套超时与取消语义 | 8 bit salt、明文协议、主线程死循环、非线程安全玩家表 |
| CatAntiCheat | 从可信玩家采样 Mod 白名单 | 白名单学习后必须进入待审，审批后才可进入强制模式 | 自动信任首个玩家、无审核直接锁定 |
| CatAntiCheat | 类空间存在性探测、运行期类加载异常检测思路 | 私有实验性传感器；仅产生观测证据，不单独自动封禁 | 有误报风险的 Attach/线程名判定和触发类静态初始化 |
| CatAntiCheat | 按检测项配置 bypass 权限 | 权限按操作和破坏性分层，密钥/封禁/截图单独授权 | 一个管理员权限包打天下 |
| GrimAC | 服务端权威、世界副本、延迟补偿、transaction 确认 | 未来移动校验的前置架构，不允许先做简单阈值后补补偿 | 没有世界状态与延迟补偿就做移动自动处置 |
| GrimAC / VelocityGuard / Cheati | violation 缓冲、干净样本衰减、set-back、按 ping 缩放容差 | 统一违规评分与处置策略；移动类永不直接自动封禁 | 单次超阈值就踢人或永久封禁 |
| Vulcan 等 | Bad Packets 类检查便宜且误报低 | 优先建设包序、字段、非法交互检查 | 先做高误报 aim/CPS 自动封禁 |
| NeoAC / Pixel's / NekoAC | modid + version + jar SHA-256 三元组、挑战绑定、心跳 | 完整性报告的统一基线 | 只校验文件名或只校验 modid |
| AntiSkidAC | 外部资源递归哈希、fail-closed、hash 更新人工审批 | 配置/资源包等影响玩法的内容纳入独立完整性域；更新走审批 | 把“无法校验”静默当成通过 |
| Darken 等 | 客户端/驱动只采集，服务端判定 | Vigil 的核心不变式 | 客户端返回结论、服务端照单全收 |
| Play Integrity | nonce 挑战、服务端验证、分级判定、先采集后执法 | 新能力先 telemetry/alert-only，校准后分级开放 | 新检测上线即自动封禁 |
| Vape 等 ghost client 的对抗经验 | 单点阈值会被“类人化”绕过 | 多窗口统计聚合、物理上限、完整性证明和人工证据链 | 宣称单一 CPS/aim 指标可稳定识别所有作弊 |
| BlackGuard / CheaterStats / MuDefender | 截图限游戏窗口、短期留存、加盐哈希、告知和申诉 | `PrivacyManifest` 驱动配置、文档、告知和审计 | 采集后再补隐私说明 |
| 公开测试实践 | 攻击 mock、协议 fuzz、网络抖动用例、夜间回归 | 固定金样本、模糊测试和六平台契约测试 | 只靠手工进服点几下就算验收 |

现有 Voidkit guard 中继续保留：签名挑战、AES-GCM、会话 nonce、随机复检、蜜罐、配置 normalize、单线程状态机、有界审计队列、SQLite WAL、后台采集。进入新实现前必须同步修正：AAD 方向/序号缺失、失败取证状态机死链、命令超时失效、全量读 jar、采集项与存储/隐私口径不一致。

## 2. 统一开发流程

| 阶段 | 主要工作 | 负责角色 | 必须交付物 | 出口门禁 |
|---|---|---|---|---|
| 0. 需求受理 | 明确威胁、玩家价值、平台范围和数据边界 | 产品负责人 + 检测负责人 | 需求卡、初始风险级别 | 目标可验证，不含“加强反作弊”这类空泛描述 |
| 1. 需求评审 | 评审架构、隐私、性能、兼容、测试和回滚 | 架构、平台、QA、安全隐私 | 评审记录、支持矩阵、验收标准 | DoR 全部满足，阻塞项为零 |
| 2. 任务拆分 | 按 core/SPI/业务/平台/测试/文档拆分依赖 | 架构负责人 + Feature Owner | 任务清单、依赖图、负责人 | 每个任务可独立验收，无隐性大任务 |
| 3. 设计定型 | 定义协议、接口、状态机、数据 Schema、降级路径 | 架构负责人 | 设计说明；必要时 ADR | 无未决策的协议/隐私/线程关键问题 |
| 4. 开发自测 | 小步提交、单元测试、静态检查、平台自测 | 开发者 | 分支、代码、测试、自测记录 | 本地/CI 基础检查通过 |
| 5. 代码评审 | 正确性、安全、并发、兼容、隐私、可维护性 | Reviewer + 领域负责人 | PR 评审记录 | 必需 reviewer 批准，无未解决阻塞意见 |
| 6. 分层验证 | 单元、契约、集成、异常、回归、压力 | QA + Feature Owner | 测试报告、样本与结果 | 质量门禁全部通过 |
| 7. 发布准备 | 构建产物、迁移、回滚、说明、监控检查 | Release Manager | Release Candidate、发布/回滚方案 | 发布检查单签署完成 |
| 8. 灰度上线 | 只采集 → 只告警 → 人工处置 → 有限自动处置 | Release Manager + 运营 | 灰度记录、指标基线 | 指标稳定，无误封/性能/隐私异常 |
| 9. 正式发布 | 全量或扩大支持矩阵 | Release Manager | Release、校验和、发布说明 | 发布验收通过，可回滚 |
| 10. 迭代复盘 | 分析误报、漏报、性能、申诉和平台问题 | 全体责任人 | 复盘、阈值/样本/文档更新 | 改进项进入需求流程，不口头遗留 |

任何阶段发现协议不兼容、隐私越界、不可回滚或服务端崩溃风险，都必须退回上一阶段，不允许“先合并再补”。

## 3. 角色与职责

小团队允许一人兼任多个角色，但**作者不能作为自己 PR 的唯一批准人**；协议、加密、隐私、自动处置和数据库迁移必须由第二名领域 reviewer 批准。

| 角色 | 主要职责 | 不可委托的验收责任 |
|---|---|---|
| 产品/运营负责人 | 玩家价值、运营规则、误封处理和发布优先级 | 需求目标、玩家告知、申诉流程 |
| 架构负责人 | 模块边界、协议、线程模型、兼容策略、ADR | 核心不变式、公开/私有边界、可回滚性 |
| Feature Owner | 需求落地、自测、文档、灰度观察 | 功能正确性和交付完整性 |
| 平台负责人 | Forge/NeoForge/Fabric 适配、工具链、契约测试 | 对应平台构建、启动和兼容结论 |
| 检测负责人 | 检测逻辑、阈值、样本、误报与漏报分析 | 证据质量，统计信号不越权 |
| QA 负责人 | 测试计划、金样本、异常/压力/回归、质量报告 | 测试证据真实完整，禁止只截成功图 |
| 安全/隐私 reviewer | 协议安全、密钥、日志、采集、留存和公开导出 | 安全与隐私签署，不可由开发自审替代 |
| Release Manager | 版本、产物、灰度、监控、回滚和发布说明 | 发布与回滚条件同时满足 |
| 文档负责人 | 文档一致性、版本支持和变更沉淀 | 文档与代码/配置同步 |

## 4. 需求评审与任务拆分

### 4.1 需求卡模板

每个需求必须包含：

1. **目标与威胁模型**：防什么、不能防什么、攻击者控制哪些环节。
2. **用户场景**：正常玩家、作弊玩家、管理员、申诉玩家分别如何使用。
3. **平台范围**：六个平台中哪些支持，哪些降级，为什么。
4. **数据分级**：
   - D0：无身份数据，如纯协议计数。
   - D1：UUID、IP、基础连接与审计。
   - D2：硬件哈希、Mod/文件清单、进程等环境数据。
   - D3：截图、全桌面、多屏等高敏感证据。
5. **判定与处置**：事实来源、服务端判定、证据级别、告警/踢出/封禁条件。
6. **失败与降级**：超时、不支持、采集失败、存储失败、队列满时怎么办。
7. **性能预算**：主线程、后台线程、CPU、内存、网络、磁盘、查询延迟。
8. **隐私要求**：采集项、告知、开关、留存、访问权限、公开版是否允许存在。
9. **测试要求**：正常样本、作弊样本、边界、异常、压力、回归和兼容组合。
10. **发布与回滚**：灰度方式、feature flag、回滚步骤、数据迁移与回退。

### 4.2 Definition of Ready

- 验收标准可执行、可观测，不使用“尽量快”“尽量准确”。
- 公开/私有归属明确，不能到开发后再决定。
- 协议、数据库、线程、隐私影响已识别。
- 测试样本和参考环境可获得。
- 不依赖未确认的第三方 API；未确认项标为阻塞或【待补充】。
- 回滚路径存在，数据库变更已有备份策略。

### 4.3 任务拆分规则

按以下顺序拆分，避免“一个 PR 同时改协议、业务和三个平台”：

1. 核心模型/协议与测试。
2. SPI/契约与 mock。
3. 单平台业务闭环。
4. 其他平台适配与契约测试。
5. 存储/迁移与异常路径。
6. 文档、监控和发布开关。

一个 PR 只解决一个主要问题。协议不兼容变更、数据迁移、自动处置策略变更必须独立 PR，便于回滚和审查。

## 5. 开发协作规范

### 5.1 分支与提交

- 私有仓 `main` 受保护；开发分支使用 `feat/<scope>`、`fix/<scope>`、`test/<scope>`、`docs/<scope>`、`chore/<scope>`。
- 禁止直接向 `main` push、禁止强制推送共享分支。
- 提交采用 Conventional Commits，如 `feat(session): add bounded handshake deadlines`。
- 公开仓只接受导出快照及公开文档/构建修正；共享代码公开 PR 必须先回port 私有主线。
- 不提交密钥、玩家数据、数据库、截图、私有部署地址或本机路径。

### 5.2 CODEOWNERS 与评审人

- `shared/protocol`、`shared/crypto`：协议/安全 reviewer。
- `server/decision`、自动处置：检测负责人 + 架构负责人。
- `storage` 和 migration：存储 reviewer + Release Manager。
- `PrivacyManifest`、截图、身份传感器：安全/隐私 reviewer。
- `platforms/<line>`：对应平台负责人。
- `sync/public-surface.yml`：架构 + 安全/隐私 reviewer。

### 5.3 设计决策

影响协议、模块边界、线程模型、数据 Schema、公开/私有边界或长期支持的决定写 ADR。ADR 记录背景、备选方案、决定、代价、回滚方式；不用聊天记录代替。

## 6. 编码与接口规范

### 6.1 Java 与模块

- 公共核心仅用 Java 8 API；构建通过 `options.release=8` 校验，禁止 records、`var`、`List.of`、`Path.of` 等。
- 1.20.x 适配层使用 Java 17，1.21.x 使用 Java 21；新语言特性不得反向渗入 shared。
- 包根为 `io.github.kansamu216.vigil`，模块包名不重叠。
- shared 不依赖 MC/加载器；client 不依赖 server；公共模块不依赖 private。
- Feature 通过 SPI 协作，禁止互相读取内部状态或直接改对方数据。

### 6.2 线程与并发

- 使用注释或项目注解明确 `@MainThread`、`@WorkerThread`、`@AnyThread`。
- 会话状态默认只在约定线程修改；后台任务只返回不可变结果。
- 禁止无界 `new Thread`、无界队列、无界 map、主线程网络/磁盘等待、主线程 `Thread.sleep`。
- 后台 executor 必须有线程上限、队列上限、拒绝策略、关闭钩子和任务超时。
- 间隔计算使用单调时钟（`System.nanoTime`）；审计时间戳才使用 wall clock。
- 主线程只做轻量状态变更；哈希、截图、进程枚举、压缩、数据库写入放在受控后台。

### 6.3 协议与加密

- 手写大端编解码，所有长度、列表数量、字符串、分片总数和总大小都有硬上限。
- 解码器必须处理：截断、负数、超长、重复、未知 id、乱序、额外尾部数据。
- AAD 至少绑定 `messageId | direction | sequence`；sequence 随会话递增且不可复用。
- nonce、reqId、sessionId 使用安全随机；认证失败按协议失败处理，不泄露内部堆栈给玩家。
- 未知消息默认忽略并记录限流审计；蜜罐 id 使用独立保留命名空间，禁止与真实消息碰撞。
- 协议 major/minor 明确；新增可选字段与不兼容变更分别处理，禁止静默改变旧版本语义。
- 私钥、会话密钥、指纹、完整报告不得写入日志或异常文本。

### 6.4 配置与 SPI

- 配置加载后统一 normalize/clamp；危险默认值必须显式说明。
- 配置重载使用快照/原子替换，不能出现半新半旧。
- SPI 只抽象实际使用能力，提供 `CapabilitySet`；不支持时显式降级和审计。
- SPI 变更需考虑二进制兼容；废弃接口先标记 deprecated，并保留约定周期。
- 错误分“玩家环境失败、协议失败、平台不支持、内部故障”，不能全部变成同一踢人原因。

### 6.5 存储与文件

- SQL 全部参数化；查询必须有索引依据和复杂度说明。
- 单写线程/受控写入、WAL、有界队列；队列满必须可观测，不能静默丢失关键封禁操作。
- migration 只向前，先备份，记录 schema 版本；禁止无备份原地改库。
- 哈希使用流式读取；截图和报告有数量/大小上限、临时文件清理和原子落盘。
- 文件权限、目录穿越、符号链接和磁盘满必须有处理。

### 6.6 隐私与日志

- 每个传感器在 `PrivacyManifest` 登记：字段、目的、分级、公开/私有、开关、留存、访问角色。
- 未登记不得采集；公开仓不得存在私有采集路径。
- 日志使用事件码和必要元数据，不写密钥、原始硬件值、完整进程清单、玩家文件内容或完整报告。
- 全桌面/多屏等 D3 采集仅私有实现，显式启用、明确告知、限制访问并有保留期。
- 内部故障默认只告警并进入降级，不得因反作弊自身异常自动永久封禁。

## 7. 代码评审

### 7.1 通用评审清单

- 需求、实现、测试、文档是否描述同一件事。
- 是否有未使用参数、死代码、空实现、静默 catch、被忽略的配置。
- 所有输入是否有边界；异常路径是否可预测。
- 是否引入新线程、全局可变状态、未清理资源或隐式单例。
- 是否保持平台无关性和公开/私有边界。
- 是否补齐正常、异常、超时、取消、重连和降级测试。
- 是否包含真实错误日志与可操作指标，而非只打印“失败”。

### 7.2 专项评审

- **协议/加密**：重放、反射、串包、序号、nonce、签名、版本兼容、密钥擦除。
- **并发**：线程归属、共享可变状态、任务取消、断线后回调、队列饱和。
- **检测**：误报来源、样本量、阈值依据、证据级别、客户端信号是否被过度信任。
- **存储**：索引、锁、事务、迁移、备份、磁盘异常、敏感字段。
- **平台**：加载器 API 用法、事件顺序、映射、客户端/服务端 dist、声明版本范围。
- **公开导出**：路径、包名、依赖坐标、文档、历史、secret 和私有策略是否泄漏。

评审意见分 `blocker` / `required` / `suggestion`。blocker 与 required 未解决不得合并，不能用口头承诺替代修改。

## 8. 测试分层与要求

| 层级 | 环境 | 必测内容 | 通过标准 |
|---|---|---|---|
| 单元测试 | 无 MC、JVM | 编解码、加密、配置、状态机、白名单、评分、超时、存储 Repository | 全部通过；覆盖率达到门禁；异常分支有证据 |
| 平台契约 | mock + 各 loader 测试环境 | join/quit、channel、调度、命令、Mod 清单、能力降级 | 六平台同一契约结果一致 |
| 集成测试 | 开发服务端 + 客户端 | 握手、断线重连、版本协商、白名单、截图、审计、迁移 | 支持矩阵内端到端闭环通过 |
| 回归测试 | 金样本库 + CI | 历史 bug、协议 golden files、误报/漏报、旧版本兼容 | 历史问题零复发，未批准行为差异为零 |
| 压力测试 | 模拟 channel/会话 + 真实端抽测 | 并发握手、包洪峰、截图分片、审计洪峰、DB 读写、线程与内存 | 不崩溃、无失控资源，满足性能预算 |
| 异常测试 | 故障注入 | 畸形包、重放、超时、磁盘满、DB 锁、进程挂起、TPS 抖动、权限失败 | 按设计降级，不崩服、不越权处置 |
| 安全/隐私测试 | 静态扫描 + 动态用例 | 篡改、重放、secret、日志、公开导出、采集开关 | 攻击样本被识别；敏感信息零泄漏 |
|  soak/灰度 | 私有 preview → 公开 beta | 真实整合包、真实延迟、申诉与运营流量 | 观察期指标稳定，才能进入自动处置 |

### 8.1 覆盖与模糊测试

- shared/core 新代码行覆盖率原则上不低于 80%；protocol/crypto/decision 不低于 90%，关键异常分支必须显式覆盖。
- 覆盖率不是免责指标，禁止为覆盖率写无断言测试。
- 每个解码器 PR 至少执行 10,000 个随机/变异输入；夜间每个解码器至少 1,000,000 个。崩溃、越界、未捕获异常、不可控内存增长均为零。
- 上述为初始门禁值，后续只能基于容量数据整体调整，不能为了让单个 PR 通过而临时降低。

### 8.2 金样本库

样本必须版本化并记录来源、预期结果和隐私级别：

- 正常：大型整合包、合法优化 Mod、不同延迟、丢包、TPS 抖动、合法 overlay、合法资源包。
- 作弊：超限 reach、timer、伪造清单、被改 Agent、重放、蜜罐回包、异常注入指标。
- 边界：空清单、超大清单、文件不可读、jar 改变 size/mtime、时钟跳变、断线重连。
- 历史：所有 P0/P1 bug 的复现样本和最小回归用例。

统计检测的正常样本自动封禁数必须为 0；合法高水平和职业式操作可以告警，但不得单独自动封禁。

### 8.3 压力与容量

先在固定参考环境建立基线，再固定 100/300/500 个模拟会话等容量档位。至少观察：主线程耗时、握手延迟、后台队列、工作线程数、堆内存、DB 延迟、磁盘和网络。

初始性能目标（首轮压测后校准，不是当前实测值）：

- 主线程周期任务 p99 ≤ 1ms，Vigil 导致的 >50ms 主线程停顿为 0。
- 缓存命中时 Mod 清单采集在后台完成，主线程等待为 0；全量采集无整 jar 读入内存。
- 审计队列有界，主线程写入不阻塞；关键封禁写失败必须显式告警。
- 无界线程、队列、会话附件和分片缓存均为 0。
- 与上一发布基线相比，关键路径退化不得超过 10%，超过需架构评审。

## 9. 必测异常场景库

每个相关 Feature 至少选择适用项，不允许只测成功路径。

1. 未装 Agent、旧/新协议、错误 nonce、重复 auth、auth 晚于 deadline。
2. 重放旧握手、旧 keepalive、旧截图分片；跨会话/跨方向/跨消息 id 包。
3. 空包、截断、超长字段、负数长度、巨大 total、重复 index、额外尾部。
4. 客户端断线、进程强杀、网络丢包、250ms+ 抖动、TPS 下降、重连与换 UUID 场景。
5. Mod 文件消失、不可读、同 size+mtime 替换、缓存损坏、全量重扫超时。
6. 截图窗口不可见、无图形环境、截图过大、分片丢失、重复、乱序、请求取消。
7. 外部命令挂起、输出超大、非零退出、命令不存在；验证超时确实能 kill。
8. SQLite 锁定、磁盘满、只读目录、损坏数据库、迁移中断、备份恢复失败。
9. 权限不足、配置非法、reload 并发、平台能力缺失、事件顺序异常。
10. 关服时有进行中任务；所有 executor、连接、文件句柄和临时文件均须释放。

内部故障期间禁止自动永久封禁；需要 fail-closed 的完整性场景必须按配置和明确错误码处理，不能把未知异常当作作弊证据。

## 10. 质量门禁

### PR 门禁

- 编译、格式、静态分析、单元测试通过。
- 模块依赖与 Java API 级别检查通过。
- 新采集项已登记 PrivacyManifest，新配置已 normalize。
- 新异常路径有测试，文档与自测记录已更新。
- secret/本机路径/玩家数据扫描通过。

### 合并门禁

- 必需 reviewer 批准，无 blocker/required。
- 受影响平台契约测试通过；shared 变更至少跑六平台契约。
- 覆盖率门禁通过，协议 golden files 无未批准变化。
- 公开/私有边界检查通过。
- 无已知 P0/P1 未解决问题。

### 夜间门禁

- 全平台集成、异常、回归、fuzz、压力测试。
- 依赖漏洞、许可证和 SBOM 检查。
- 长运行资源曲线无持续增长，历史误报样本零自动封禁。

### 发布门禁

- P0/P1 为 0，P2 有明确负责人和处置决定。
- QA、Feature Owner、安全/隐私、Release Manager 签署。
- 产物哈希、SBOM、发布说明、支持矩阵、迁移和回滚方案齐全。
- 已演练“关闭自动处置”和“回退上一版本”，不是只写文档。
- 公开导出：allowlist、共享哈希 parity、公开独立构建、私有路径/依赖/历史/secret 检查全部通过。

## 11. 发布验收与灰度

### 11.1 发布物

每个平台线分别提供：server/client jar、SHA-256、SBOM、协议版本、兼容矩阵、配置变更、数据库 migration、已知限制、回滚版本。

### 11.2 灰度顺序

1. **只构建/启动**：不处理玩家，验证资源与兼容。
2. **只采集**：只记录遥测，不告警、不处置。
3. **只告警**：管理员可见，评估误报和告警流量。
4. **人工处置**：由管理员根据报告处理。
5. **有限自动处置**：仅限确证级证据，保留总开关和分平台开关。

跳过灰度级别必须由架构、检测和 Release Manager 共同批准。

### 11.3 发布验收

- 支持矩阵内正常客户端握手与重连通过，版本不匹配有明确提示。
- 异常包和内部故障不导致 MC 服务端崩溃。
- 正常金样本自动误封数为 0；告警噪声在可运营范围内。
- 性能满足预算，监控和告警能实际触发。
- 隐私告知、采集开关、留存清理、访问权限和申诉通道可用。
- 回滚演练成功，旧数据可恢复或旧代码可读取新 Schema。

---

## 12. 监控与告警

### 12.1 必采指标

- 握手：尝试/成功/失败、失败码、协议版本、各阶段耗时、超时和重连。
- 会话：各状态数量、keepalive 失败、复检结果、未知消息与蜜罐事件。
- 检测：各检查告警数、证据级别、处置数、人工撤销数、申诉与误报。
- 客户端采集：哈希耗时、缓存命中、扫描失败、截图失败、平台降级。
- 性能：主线程耗时、worker 线程、队列深度/丢弃、堆内存、网络与分片大小。
- 存储：读写延迟、锁/失败、DB 大小、备份结果、磁盘使用。
- 发布：产品/协议版本分布、平台分布、自动处置开关状态。

指标不得包含原始硬件标识、QQ/微信、完整进程名清单、完整报告或密钥。

### 12.2 初始告警规则

以下为首版默认值，形成真实基线后统一校准：

- 任何 Vigil 导致的服务端异常退出、隐私泄漏或 secret 泄漏：**立即最高级告警并停止发布**。
- 数据库写失败、迁移失败、备份失败：**立即告警并进入降级**。
- 审计队列出现丢弃：警告；持续丢弃或关键封禁写失败：严重。
- 主线程 p99 连续超过预算：警告；出现 >50ms 停顿：严重并考虑回滚。
- 握手成功率较基线显著下降、踢出率或某失败码异常翻倍：暂停灰度。
- 同一正常样本重复误报、申诉异常增加：停止自动处置，进入人工复核。
- 公开导出检查失败：禁止发布，不允许人工忽略。

监控必须定期做故障注入，证明告警链真的能到达负责人。

## 13. 故障回滚与应急

### 13.1 触发条件

服务端崩溃或明显 TPS 回退、握手大面积失败、误封、隐私/secret 泄漏、数据库损坏、关键功能不可用、发布指标显著偏离基线。

### 13.2 回滚步骤

1. **止损**：冻结发布，关闭新检测和自动处置；必要时切到 alert-only。
2. **保全证据**：保存日志、指标、配置、审计和数据库快照，限制敏感证据访问。
3. **恢复兼容**：按平台回退到上一已验证 server/client 产物；不要盲目全平台一起回退。
4. **处理数据**：若 migration 影响兼容，恢复备份或切换到能读取新 Schema 的兼容版本。
5. **验证**：检查握手、主线程、存储、误封和队列；确认服务稳定后再开放处置。
6. **通知**：管理员获知原因、影响范围、玩家申诉路径和后续计划。
7. **复盘**：形成时间线、根因、回归样本、永久修复和预防措施。

协议 major 不兼容时，回滚必须考虑新旧客户端组合。发布前必须保留上一兼容产物，不能用“重新编译旧代码”作为唯一回滚方案。

### 13.3 降级原则

- 存储故障：保留内存态必要能力，停止依赖持久证据的自动封禁。
- 传感器故障：该传感器标记不可用，不把它当成“干净”或“作弊”。
- 平台故障：只隔离对应平台，不拖垮其他平台。
- 无法判断时优先玩家体验与人工复核，不以反作弊自身故障惩罚玩家。

## 16. 总体 Definition of Done

一个功能只有同时满足以下条件才算完成：

1. 代码、测试、配置、文档、监控全部交付。
2. 支持矩阵内验证通过，不支持平台有明确降级。
3. 正常路径、异常路径、故障降级和回滚均可重复验证。
4. 没有隐私未登记、公开边界破坏、敏感日志或未评审自动处置。
5. 性能预算达标，无资源失控和主线程重活。
6. 有发布方式、观察指标、负责人和回滚方案。
7. 公开导出可独立构建，私有实现与历史未泄漏。

只完成代码并通过编译，不算完成；只在单一 NeoForge 版本跑通，不算六平台完成；只验证“能抓到作弊”，没有误报和异常验证，不算达到发布标准。

## 17. 首轮落地顺序

1. 将本规范中的模块依赖、Java API、公开导出和 CI 检查先自动化。
2. M0 空 Mod 阶段即建立六平台契约测试和启动 smoke test。
3. M1 协议阶段建立 golden files、fuzz、会话状态机与异常样本。
4. M2 公开 MVP 阶段建立真实端集成、性能和隐私验收。
5. M3 私有能力迁移阶段补齐故障注入、公开导出、灰度与回滚演练。

后续新增检测一律沿“需求卡 → 设计评审 → 样本先行 → 实现 → 分层验证 → alert-only → 分级发布”的路径执行。
